# Rails assumptions in the flows

_Generated by `scripts/rails_assumptions.py` from the committed policy `docs/architecture/rails-assumptions.policy.json`; do not edit. `python3 scripts/rails_assumptions.py --check` fails when this page is stale._

Slice 2 of the `nextjs-stack` epic (#2162, #2164). `plugin-boundaries` rule 1: the flows stay one stack-neutral core, so every place they assume Rails gets one decision. The scan finds the lines that **name** a Rails thing (a CLI, a gem, a Rails path, the framework); the decision per file is a person's, made by reading it, with the reason in the policy. A flow that assumes Rails without naming it is not found here.

## Decisions

| decision | what it means |
|---|---|
| `rails-stack` | exists only for Rails projects; moves to `rails-stack` and registers through its manifest |
| `detector` | flow logic that hardwires a Rails command or path; stays and asks the stack detector (#2163) |
| `reword` | prose or metadata that says Rails and drives no behaviour; reworded where the file is next touched |
| `neutral` | incidental hits (an example, a fixture, a fragment of another word); nothing to change |

The counts (files and lines per decision, per flow, per thing named) are not stored in this page or in `rails-assumptions.json`: a stored total is a line every pull request rewrites. `python3 scripts/rails_assumptions.py --status` computes them from the inventory below. A line that names two things counts once per category it names there and once overall.

## setup-flow, section by section (issue #2180)

/rails-flow:setup-flow is the shipped home of a project's working rules (git flow, guardrails, parallel sessions, labels, who merges). Today it reads the Gemfile, the Rails version and the rails-8 skill to fill them, and the second half of the file is a list of Rails-only repairs. The rule scaffold itself names no stack; the stack facts and the Rails repairs are what assume Rails.

| lines | Rails hit lines | what it assumes | decision | how |
|---|---:|---|---|---|
| 308-531 | 7 | path-scoped rules over app/models/**/*.rb and **/*.rb, config/database.yml as the database marker, config/ci.rb and bin/ci, and the one RAILS_ENV=test bin/rails command guard-bash allows | `detector` | globs, database marker and the allowed test-prep command come from the descriptor |
| 532-760 | 9 | companion workflows: bundle exec rspec, rubocop, bundler-audit, brakeman, the architecture graph over routes/app/db, derived docs over db/schema.rb and Gemfile.lock, the help registry rake task | `detector` | suite, lint and security commands come from the descriptor; the graph and help registry are the rails-docs-generators move |
| 761-1001 | 7 | what stays of §8 after the Rails-only repairs moved: the CI economy section's 'the Rails 8 default' ci.yml and `bin/ci`, the doctrine gate's Brakeman and 'no Ruby' wording | `reword` | the Rails-only repairs moved to rails-stack's setup/rails.md, which §0 runs as Rails' setup_section (#2180); what is left names Rails in wording only |

**Proposal for a `nextjs-stack` repo.**

- Split the file by who owns the content: the stack-neutral rule scaffold (git flow, guardrails, parallel sessions, labels, who merges) stays in rails-flow's setup-flow and names no stack; each stack plugin ships its own scaffold section.
- setup-flow asks the detector (#2163) which stacks the repository holds (more than one is allowed), fills the stack line, commands, source globs and database marker from the descriptor, and then runs each stack's section in turn.
- For a nextjs-stack repository that means: the same rule scaffold; stack facts from package.json, next.config and supabase/ as the detector reports them; and nextjs-stack's section proposing its own repairs (strict TypeScript, Storybook, local-first CI) as approved diffs, the way the Rails repairs are proposed today.
- A project's rules arrive by running setup-flow, not by a hand-written copy: a repository adopting the rules (flo-it-ui, for one) gets the neutral scaffold plus its stack section, and a later release updates it the same idempotent way.
