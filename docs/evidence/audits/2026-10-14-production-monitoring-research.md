## 1. DB signals, overhead, privacy

### 1a pg_stat_statements (PG18 doc https://www.postgresql.org/docs/current/pgstatstatements.html)
- V Row key = (dbid, userid, queryid, toplevel). Constants become $1..; numbering starts after the highest $n already in the text. Long IN lists squashed to `IN ($1 /*, ... */)`.
- V The displayed text is the FIRST query seen for that queryid. Safe to publish only if it was normalised; utility statements are not (already in our file).
- V queryid is derived from the post-parse tree, so it depends on OIDs: drop/recreate a function changes it, a table may not. Platform-sensitive. Same on physical replicas (expected), not guaranteed on logical replicas, not guaranteed across MAJOR versions. => A fingerprint stored on an issue must be re-resolved after a major upgrade or a function recreate. Dedupe key should be (queryid + normalised-text hash), not queryid alone.
- V Columns useful for ranking: calls, total_exec_time, mean/stddev/min/max_exec_time, rows, shared_blks_hit/read (docs give `100.0*hit/nullif(hit+read,0)` hit_percent), temp_blks_read/written, wal_bytes, plans/total_plan_time (needs track_planning), stats_since and minmax_stats_since (so a window is known), jit_* columns, parallel_workers_to_launch/launched (PG18).
- V pg_stat_statements_info.dealloc counts evictions when more than pg_stat_statements.max (default 5000) distinct statements; a rising dealloc means ranking misses the tail. stats_reset gives the window start.
- V Overhead: track_planning default off, "can cause noticeable contention with many concurrent connections". track_io_timing default off, "may cause significant overhead on some platforms"; measure with pg_test_timing (https://www.postgresql.org/docs/18/runtime-config-statistics.html). Shared memory scales with .max even if track=none.
- V Query texts live in a disk file; if it grows too large texts may be discarded and `query` shows NULL while stats stay. `pg_stat_statements(showtext := false)` skips reading text (cheap bulk reads; fetch text only for the top N).
- V Privacy/privilege: only superuser or pg_read_all_stats sees other users' text and queryid. pg_stat_statements_reset(userid,dbid,queryid,minmax_only) returns a timestamp; superuser by default. Do NOT reset from the monitoring job: store deltas between snapshots instead.
- V compute_query_id default auto (pg_stat_statements turns it on) (runtime-config-statistics page).
- R Delta approach: snapshot (queryid, calls, total_exec_time, rows, blks) every N min into the app's own table; rank by delta total_exec_time over the window, not lifetime. pghero's capture_query_stats does this (V, see 1e).

### 1b auto_explain (https://www.postgresql.org/docs/current/auto-explain.html, PG18)
- V Does nothing until auto_explain.log_min_duration is set (default -1). Preload via session_preload_libraries (or shared_preload_libraries); only superusers change parameters.
- V sample_rate default 1 (fraction of statements per session explained). log_analyze default off and costly: "per-plan-node timing occurs for all statements executed, whether or not they run long enough to actually get logged. ... extremely negative impact". Mitigate with log_timing=off (row counts only), log_buffers, log_format json, log_nested_statements off.
- V log_parameter_max_length default -1 = parameter values logged in full => PII in logs. Set 0 (or small).
- V Safe production recipe (design, built from the verified parameters): log_min_duration=1s..3s, log_analyze=on only with sample_rate<=0.05 and log_timing=off, log_parameter_max_length=0, JSON format, ship the log through a scrubber. Without log_analyze it is plain EXPLAIN (no actuals): cheap but weaker evidence.
- V Companion for the plain log: log_min_duration_statement (default -1), log_min_duration_sample + log_statement_sample_rate (sampled below the hard threshold), log_lock_waits (default off, logs waits > deadlock_timeout), log_temp_files (default -1), log_parameter_max_length (default -1, logs binds in full). Page warns log_statement "might reveal sensitive data and even contain plaintext passwords" (https://www.postgresql.org/docs/18/runtime-config-logging.html).

### 1c Table/index usage (https://www.postgresql.org/docs/current/monitoring-stats.html, PG18)
- V pg_stat_user_tables: seq_scan, last_seq_scan, seq_tup_read, idx_scan, last_idx_scan, idx_tup_fetch, n_live_tup/n_dead_tup (ESTIMATES), n_mod_since_analyze, last_autovacuum/last_autoanalyze, total_autovacuum_time. pg_stat_user_indexes: idx_scan, last_idx_scan (timestamp, new column), idx_tup_read/fetch.
- V Counters are in shared memory; kept on clean shutdown; ALL reset after crash, base-backup start or PITR; flushed at most once per second per process; cached to end of transaction (stats_fetch_consistency). Caveat for index-removal findings: unused = idx_scan 0 (or last_idx_scan old) over a window that has not been reset; check stats_reset in pg_stat_database and the failover history first.
- V "Each index search increments idx_scan" so idx_scan can exceed the number of scan-node executions; bitmap scans bump idx_tup_read but not idx_tup_fetch. Do not use idx_tup_* ratios as precision.
- V On a standby: stats are active and record that standby's scans/reads/index usage, but WAL replay does not increment n_tup_* or pg_statio; autovacuum is inactive so last_vacuum is not maintained; pg_stat_statements loads and works (https://www.postgresql.org/docs/18/hot-standby.html). => Index usage seen on a replica reflects only the replica's read traffic; the unused-index verdict must use the primary (or every node that serves reads).
- R Seq-scan ranking: seq_scan > 0 AND seq_tup_read/seq_scan large AND n_live_tup > ~10k, joined to a pg_stat_statements query that touches the table. A tiny table with seq_scan is correct, not a finding.
- R Missing-index candidates: foreign keys with no leading-column index (catalog query via pg_constraint/pg_index, no stats needed). Duplicate: identical indkey/indclass/indpred pairs. Unused: idx_scan=0 AND NOT indisunique AND NOT backing a constraint AND size above a floor. Invalid: pg_index.indisvalid=false (failed CONCURRENTLY build).
- V pghero 4.0 added `unused_index_megabytes` (floor on unused-index size) and `disable_kill` (turn off its query/connection kill buttons) (https://raw.githubusercontent.com/ankane/pghero/master/CHANGELOG.md, 4.0.0 2026-08-05; 4.0.1 2026-08-15).

### 1d Bloat, locks, connections
- V pgstattuple: "always performs a full-table scan"; pgstattuple_approx uses the visibility map, exact dead-tuple counts, ESTIMATED live/free space; execute restricted to pg_stat_scan_tables (https://www.postgresql.org/docs/18/pgstattuple.html). => never run pgstattuple on a big prod table from the monitor; use n_dead_tup/n_live_tup + autovacuum timestamps as the cheap screen, pgstattuple_approx per flagged table.
- V pg_monitor = member of pg_read_all_settings, pg_read_all_stats, pg_stat_scan_tables; pg_stat_scan_tables "may take ACCESS SHARE locks on tables, potentially for a long time" (https://www.postgresql.org/docs/18/predefined-roles.html). Least-privilege: grant pg_read_all_stats (+ pg_read_all_settings), NOT pg_monitor, unless bloat functions are needed.
- V Lock waits: pg_stat_activity.wait_event_type='Lock' (state and wait_event are independent, not synchronised); log_lock_waits for history; pg_stat_database.deadlocks, temp_files/temp_bytes (since last reset) (monitoring-stats page).
- V idle_in_transaction_session_timeout default 0; an idle open transaction blocks vacuum of recently-dead tuples (=> bloat). statement_timeout / lock_timeout default 0, docs advise against setting them in postgresql.conf; set per role (https://www.postgresql.org/docs/18/runtime-config-client.html).
- R Connection saturation = count(*) from pg_stat_activity (by state) vs max_connections, plus Rails pool wait (`ActiveRecord::ConnectionTimeoutError` count, pool.stat busy/waiting). Not fetched.

### 1e Tools
- V PgHero (4.0.1, 2026-08-15): needs PG >=14 and pg_query >=6 since 4.0; Rails >=7.2 and Ruby >=3.3 since 3.8.0. Stats history: schedule `rake pghero:capture_query_stats` every 5 min; `pghero:clean_query_stats KEEP_DAYS=14`; `PGHERO_STATS_DATABASE_URL` stores stats elsewhere; index suggestions need pg_query and query stats; auth via PGHERO_USERNAME/PASSWORD or Devise-wrapped mount; "create a dedicated database user" (https://raw.githubusercontent.com/ankane/pghero/master/guides/Rails.md, README https://github.com/ankane/pghero). The guide says nothing on replicas or alerting (fetched text), so claims about those are unknown.
- V Dexter: HypoPG hypothetical indexes over pg_stat_statements/logs; report-only unless `--create` (CREATE INDEX CONCURRENTLY); `--min-calls`, `--min-time` (minutes) filter one-offs (https://github.com/ankane/dexter). Use as an evidence source (index candidate + estimated cost drop), never `--create` in prod from an agent.
- V pg_stat_kcache: per-queryid CPU user/system and physical reads/writes, requires pg_stat_statements first in shared_preload_libraries, PG>=9.4 (plan tracking >=13), README gives no overhead figures (https://github.com/powa-team/pg_stat_kcache). Optional; distinguishes CPU-bound from disk-bound queries. Managed-DB availability unknown (not in README).

## 2. Page / process / job level

- V Rails Pulse (https://github.com/railspulse/rails_pulse; released version and date NOT shown on README): normalised+fingerprinted SQL with counts and P95 per statement shape, N+1 patterns, EXPLAIN plans, index suggestions; jobs duration/queue wait/failure rate on any Active Job adapter; capture queued off request thread, dropped not blocked under load (load shedding, NOT sampling: README describes no sampling option); retention by age and row count; separate DB supported; "Thresholds for slow, very slow and critical, service level objectives per percentile" live in the initializer but names/defaults are only in the external docs (railspulse.com/documentation/advanced, not fetched). README does not describe literal redaction for SQL.
- V Sentry N+1 detector rule (https://docs.sentry.io/product/issues/issue-details/performance-issues/n-one-queries/): sequential non-overlapping DB spans with similar descriptions; combined duration >50 ms; span count above a threshold "usually five"; spans need the full parameterised text; grouped into an issue by fingerprint of parent span + source span + repeating spans; thresholds tunable in Project Settings > Performance. Good template for our own N+1 threshold: >=5 repeats AND >=50 ms total, so alert noise is bounded.
- V Sentry tracing: `traces_sample_rate` (0-1) or `traces_sampler` (sampler wins if both set); docs say test before enabling in high-throughput apps, no overhead figure (https://docs.sentry.io/platforms/ruby/guides/rails/tracing/).
- V OTel Ruby head sampling via `OTEL_TRACES_SAMPLER=traceidratio` + `OTEL_TRACES_SAMPLER_ARG=0.1`; head samplers decide at span start, so "slow only" selection needs a span processor/tail sampling (https://opentelemetry.io/docs/languages/ruby/sampling/; page did not mention parentbased_traceidratio, so that name is R).
- V Prosopite (https://github.com/charkost/prosopite): N+1 = several queries with the same call stack AND same fingerprint; min_n_queries default 2; allow_stack_paths / ignore_queries to silence; README shows dev/test only (`unless Rails.env.production?`), says nothing about production use, sampling or overhead. => Production N+1 detection should come from the APM/Pulse/OTel spans (sampled), not Prosopite. Prosopite's value is a regression test after the fix.
- V Rails config (https://guides.rubyonrails.org/configuring.html): query_log_tags default tags application/controller/action/job; query_log_tags_format :sqlcommenter for load_defaults >=7.1; enabling query_log_tags disables DB prepared statements; `:source_location` tag "can be slow" in production; cache_query_log_tags default false; verbose_query_logs false outside development; strict_loading: action_on_strict_loading_violation default :raise (can be :log), strict_loading_mode :all or :n_plus_one_only, strict_loading_by_default false. => In prod set strict_loading to :log + :n_plus_one_only for a sampled signal (design; the combination is R for behaviour).
  - Mechanism that matters for the pipeline: query_log_tags append a /* controller:...,action:... */ comment to SQL; pg_stat_statements normalises it away from the queryid? R/UNVERIFIED: comments are not part of the post-parse tree so the queryid should be unchanged and the stored `query` text of the first-seen statement keeps its comment. Measure before relying on it (this is how a call site gets attached to a queryid without a trace).
- V Solid Queue README (https://github.com/rails/solid_queue): documents no latency/queue-depth metrics API and one event only (`fail_many_claimed.solid_queue`); tables solid_queue_ready_executions, scheduled_executions, failed_executions named; heartbeat 60 s, alive threshold 5 min; lifecycle hooks (on_start...) are the stated place for metrics; Rails.error reporting via on_thread_error. mission_control-jobs for the UI. => Queue depth/latency must be computed by us from the tables (R: ready_executions.created_at age = queue wait; claimed_executions; jobs.finished_at - created_at) or from Active Job `perform.active_job` / `enqueue.active_job` events (already in observability.md §2).
- V Solid Cache README (https://github.com/rails/solid_cache): no hit-rate or stats API, no event catalogue; only `active_record_instrumentation` (default true), max_age default 2 weeks, max_size default nil, expiry triggered by a write counter reaching 50% of expiry_batch_size. => Hit rate comes from Rails' `cache_read.active_support` payload `:hit` (our file L75) per cache key family; Solid Cache does not report it itself.
- V Honeybadger: the docs page fetched had nothing on Insights/sampling (nav mentions "Sampling events" and "Rails Metrics"; contents not read). No claim made.
- R Percentiles: compute p50/p95/p99 per route (controller#action, not URL) and per job class from a histogram; alert on p95 of a route only with n >= a floor (e.g. 50 requests/window), relative to its own 7-day baseline (>1.5x and above an absolute floor), 3 consecutive windows, one issue per route+queryid, not per occurrence. Percentiles of percentiles are invalid: aggregate histograms or raw durations.
- R Noise controls: ignore health checks and /rails_pulse itself; separate cold-start/deploy windows (deploy markers); exclude requests with 5xx from latency; cap new issues per run (e.g. 5) and rank by total time consumed (calls x mean), because a slow rare query rarely matters.

## 3. Safe pipeline

Design (ours; each step names what backs it):
1. Scheduled read-only job (Solid Queue recurring or external cron) connecting as a dedicated role. V role scope: `GRANT pg_read_all_stats` (and pg_read_all_settings if settings are read), `ALTER ROLE monitor SET statement_timeout='5s'`, `SET lock_timeout='1s'`, `idle_in_transaction_session_timeout`, `default_transaction_read_only=on` (R for that last setting; statement_timeout/lock_timeout per-role advice V from runtime-config-client page). No superuser, no table SELECT on app data, no pg_monitor (pg_stat_scan_tables lock caveat V).
2. Run it against a read replica when one exists. V standby facts: stat views and pg_stat_statements work there but reflect only that node's reads; replay does not bump n_tup_*; autovacuum info absent; queries can be cancelled by recovery conflicts (max_standby_streaming_delay; cancels counted in pg_stat_database_conflicts); data is eventually consistent; serializable unavailable. => Use the replica for EXPLAIN/size/bloat reads of REPLICATED data; read pg_stat_statements from EVERY node that serves app traffic (primary's view lacks replica-served queries). Never `EXPLAIN ANALYZE` on prod primary from an agent; `EXPLAIN (ANALYZE)` runs the statement (V; wrap DML in BEGIN/ROLLBACK, V).
3. Evidence capture per finding:
   - Normalised SQL only: take `query` from pg_stat_statements for data statements (track_utility off, V), never from pg_stat_activity/logs/auto_explain output (literals and bound params; V auto_explain and log_parameter_max_length defaults log in full).
   - Plan: `EXPLAIN (GENERIC_PLAN)` on the $n text (V: allowed with $1 placeholders, cannot combine with ANALYZE; version-added not stated on page, added in PG16 per R). Generic plan can differ from the custom plans actually used for skewed params; label it "generic". For actuals use auto_explain JSON (scrubbed) on a sample.
   - Metric before: delta over window: calls, total/mean/p95-ish (stddev, max available; true p95 is NOT in pg_stat_statements: V columns are min/max/mean/stddev only), rows per call, hit_percent, temp_blks_written, window start (stats_since/snapshot ts).
   - Call site: from query_log_tags comment (controller/action/job) or APM span/backtrace; never from user data.
   - Table facts: size, n_live_tup, seq_scan/idx_scan counts, existing index defs.
4. Dedupe: key = sha256(normalised text with comments stripped) + queryid + schema fingerprint; store key in a marker line in the issue body; look up open AND recently closed issues by marker (bounded `gh issue list --limit`). Re-open/comment instead of new issue when the metric regresses after a fix; suppress when closed < N days unless delta worse than the post-fix value. queryid unstable across major versions/function recreation (V) so include the text hash as the second key.
5. Issue body: sentence + metrics table + normalised SQL + EXPLAIN + call site + suggested fix class from the fix menu (section 4) + "how to verify" (the same snapshot query and threshold). No param values, no emails/ids, no raw log lines. Run a PII scrubber on the body (regex for emails, long digit strings, quoted literals) and fail closed (file nothing) if it matches, same stance as the repo's alert rule (observability.md L579).
6. Agent fixes in a branch; verification MUST be measured not asserted: (a) reproduce the plan change on a staging copy with production-like row counts (EXPLAIN ANALYZE there is safe); (b) a regression test (Prosopite scan for N+1, V; or a spec asserting query count / `assert_queries_count`-style, R); (c) after deploy, the monitor compares post-deploy delta to "before" over an equal-traffic window and comments pass/fail on the issue; auto-close only on pass, with minimum calls floor so a quiet window cannot "pass".
7. Guard rails: cap findings per run; never let the job create/drop indexes; index creation by agent migration only (`algorithm: :concurrently` + disable_ddl_transaction!, R) and `Dexter --create` not used.

Privacy summary (V unless noted): pg_stat_statements text normalised for DML but not utility; first-seen text is shown; auto_explain and statement logs log bind values in full by default; Rack OTel span records the query string (already in our file); Rails Pulse README says no data leaves your servers but describes no SQL literal redaction; Sentry N+1 grouping depends on parameterised text.

## 4. Fix menu for agents, order and evidence

Order (design; the existing performance-caching.md §7 already says "fix queries before adding caches" V-in-repo):
1. Index (add / composite / partial / covering; or DROP unused). Evidence: plan shows Seq Scan or Sort on a large table with a selective filter; rows removed by filter >> rows returned; table n_live_tup large; mean_exec_time x calls ranks high; no existing index with that leading column (catalog query); for a new index: Dexter/HypoPG estimated cost drop (V tool) and EXPLAIN on staging after creation; write-cost check (n_tup_ins+upd rate on that table). For a drop: idx_scan=0/last_idx_scan old over an un-reset window on EVERY serving node, not unique, not constraint-backing, size above floor (V counters caveats).
2. Query rewrite (remove SELECT *, OFFSET -> keyset, OR/ILIKE/function-on-column, correlated subquery, COUNT(*) -> EXISTS, IN-list size). Evidence: plan node that is the cost, rows/call, temp_blks_written > 0 (sort/hash spills) (V column), shared_blks_read high with low hit_percent.
3. N+1 eager load (`includes`/`preload`/`eager_load`, strict_loading). Evidence: >=5 near-identical statements per request/trace totalling >=50 ms (Sentry rule V), same call stack + same fingerprint (Prosopite rule V); calls per request from traces; fix proof = a Prosopite/strict_loading test that fails before and passes after.
4. Counter cache / denormalised column. Evidence: repeated COUNT(*) on an association in list pages (high calls, small mean), read:write ratio high; cost: write amplification and drift (need backfill + `reset_counters`). Mechanism per existing file L178-190.
5. Cache: HTTP (fresh_when) -> fragment -> low-level (existing file L251-252). Evidence: the query/render is already efficient (plan fine) but called for identical inputs; measured hit rate target from `cache_read.active_support :hit` (V payload field in our file L75); invalidation key identified. Never first fix for an unindexed or N+1 query (cache hides the bug, existing L250).
6. Materialised view / summary table. Evidence: aggregate over large range read often, tolerance for staleness stated by the owner (product rule: ask the OWNER), refresh cost estimated. V: REFRESH ... CONCURRENTLY needs at least one UNIQUE index on plain columns (no expression, no WHERE), view must be populated, only one refresh at a time; non-concurrent refresh can block readers (https://www.postgresql.org/docs/18/sql-refreshmaterializedview.html). Also: refresh job duration becomes a new slow job to monitor.
7. Out-of-band structural levers (only on named evidence): partitioning, connection pool/PgBouncer for saturation, vacuum tuning for bloat/idle-in-transaction (V idle-in-tx blocks vacuum), pagination/limit at UX level.
Each menu entry must carry: precondition evidence (above), the change, the verification query, the rollback (drop index concurrently / revert), and the risk note (lock, write cost, staleness).
