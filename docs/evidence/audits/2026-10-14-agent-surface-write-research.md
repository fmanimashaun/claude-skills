## 1. MCP spec for state-changing tools

Tools page, https://modelcontextprotocol.io/specification/2026-07-28/server/tools (VERIFIED; no page date/version beyond the URL revision):
- Annotations: "clients MUST consider tool annotations to be untrusted unless they come from trusted servers." (as fetched)
- Annotation defaults are NOT on this page. schema.ts (VERIFIED, https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2026-07-28/schema.ts, as fetched): `readOnlyHint` default false ("does not modify its environment"); `destructiveHint` default true, only meaningful when readOnlyHint is false; `idempotentHint` default false, only meaningful when readOnlyHint is false ("no additional effect" on repeat with same arguments); `openWorldHint` default true; `title` display name. All are "hints"; clients "should never make tool use decisions" on annotations from untrusted servers.
- What the annotations do NOT say: nothing in schema.ts or the tools page says a client must prompt for `destructiveHint: true`, or skip a prompt for `readOnlyHint: true`. The prompt language is separate (below).
- Human in the loop (User Interaction Model, warning box): "there SHOULD always be a human in the loop with the ability to deny tool invocations"; applications SHOULD "present confirmation prompts to the user for operations". Security Considerations: clients SHOULD "Prompt for user confirmation on sensitive operations", "Show tool inputs to the user before calling the server", "Log tool usage for audit purposes". These are CLIENT obligations; the page also says the protocol "does not mandate any specific user interaction model".
- Server MUSTs (Security Considerations): "Validate all tool inputs; Implement proper access controls; Rate limit tool invocations; Sanitize tool outputs". Nothing on idempotency, audit rows server-side, or confirmation by the server.
- Errors: two channels. Protocol errors (unknown tool, malformed request, server errors) are JSON-RPC errors "that models are less likely to be able to fix". Tool execution errors (API failures, input validation, "Business logic errors") go in the result with `isError: true` and "actionable feedback". Clients SHOULD pass execution errors to the model. The page does not classify an authorization refusal of a write; schema.ts says errors originating from the tool SHOULD be in the result. A refused write as `isError` vs an HTTP 403 is therefore not decided by the page (the downstream app we know of answers a role that lacks a tool with HTTP 403).
- tools/list MAY vary by the authorization on the request ("returning only the tools the caller's granted scopes permit"); MUST NOT vary per connection.
- "Stateful Tools" section (VERIFIED, as fetched): "non-normative guidance". "The protocol has no concept of a state handle". Handles: "a handle is a name, not a capability. The server should validate the caller's authorization against the handle on every call" (for authenticated servers); opaque; state the lifetime in the creation tool's description; an expired/unknown handle should return a tool execution error.
- State Handle Hijacking, https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices (VERIFIED, as fetched): servers that implement authorization "MUST verify all inbound requests" and "MUST NOT treat possession of a state handle as authentication"; SHOULD use secure random handles; "Expiring handles can also reduce the risk"; SHOULD bind handles server-side to the authenticated user, e.g. key `<user_id>:<handle>` with the user ID "derived from the verified token rather than supplied by the client". A preview-then-confirm token is a state handle under this text [Inferred: the page names carts and workflow IDs, not confirmations].
- Elicitation, https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation (VERIFIED): two modes, form (flat primitive schema) and url (out-of-band). Delivered inside an `InputRequiredResult` containing `elicitation/create`; client retries `tools/call` with `inputResponses`. Actions accept / decline / cancel ("User clicked Submit, OK, Confirm"). Clients declare the `elicitation` capability per request; "Servers MUST NOT send elicitation requests with modes that are not supported by the client." Servers "MUST handle cases where the user declines or cancels". Form mode MUST NOT carry secrets/credentials. Servers "MUST bind elicitation requests to the client and user identity" and "MUST NOT rely on client-provided user identification". The page does not say elicitation is for confirming writes; its examples are data collection. What a server does for a client without the capability: MRTR page (VERIFIED, https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr): "if a client does not declare support for `elicitation`, the server MUST NOT include any `elicitation/create` requests". The spec gives no fallback; a server with no other confirmation channel has to refuse, proceed, or use its own mechanism (our design).
- MRTR `requestState` (same page, VERIFIED): "MUST treat `requestState` as an attacker-controlled input"; if it influences authorization or business logic, servers "MUST protect its integrity (e.g. HMAC or AEAD)"; SHOULD include the authenticated principal, a short expiry, and an identifier/digest of the originating request; "these measures ... do not by themselves guarantee single-use": one-time redemptions "MUST" be enforced server-side. Servers "MUST NOT assume that clients will fulfill the inputRequests or retry". This is the spec's own text for a confirm-then-retry write; it is the closest primary source to a "preview token".
- Rate limiting: only the one-line MUST above (VERIFIED). No numbers, no per-principal rule.
- Scope step-up, https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization (VERIFIED, as fetched): runtime insufficient scope SHOULD be `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="...", resource_metadata=...`; SHOULD include all scopes for the current operation in one challenge; "Clients acting on behalf of a user SHOULD attempt the step-up authorization flow"; clients SHOULD cap retries; "Servers MUST account for scope hierarchies". Authorization itself is "OPTIONAL" for MCP; HTTP transports SHOULD conform. Scope Minimization (security best practices page, VERIFIED): "Minimal initial scope set (e.g., `mcp:tools-basic`) containing only low-risk discovery/read operations; Incremental elevation via targeted WWW-Authenticate scope challenges when privileged operations are first attempted"; common mistake: "Treating claimed scopes in token as sufficient without server-side authorization logic"; "Log elevation events (scope requested, granted subset) with correlation IDs". The spec defines no per-tool scope naming scheme.
- Async/long-running writes: the 2026-07-28 spec tree has NO tasks page. llms.txt (VERIFIED, https://modelcontextprotocol.io/llms.txt, as fetched) lists Tasks only as spec page 2025-11-25/basic/utilities/tasks and as an EXTENSION, https://modelcontextprotocol.io/extensions/tasks/overview (VERIFIED, unversioned page): extension id `io.modelcontextprotocol/tasks`, opt-in by both sides (client sends it in per-request capabilities; "Never return a task to a client that did not declare support"); `tools/call` may return `CreateTaskResult` (`taskId`, status working / input_required / completed / failed / cancelled, `ttlMs`, `pollIntervalMs`); `tasks/get`, `tasks/update`, `tasks/cancel`; cancellation "cooperative". The page names "bulk imports, mass updates" and "approval gates" as use cases. It says nothing on idempotency or on who may read a task id (authorization of task ids: NOT FOUND on that page; the spec text is in github.com/modelcontextprotocol/ext-tasks, not opened).
- "Does the 2026-07-28 revision define task/async operations?" As an extension, not in the revision's own page tree. Ruby SDK nav has no Tasks page (see Q6).

## 2. Safe write patterns (what the source says; what it does NOT say about agents)

Idempotency keys
- IETF draft-ietf-httpapi-idempotency-key-header (VERIFIED, https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/ and archive `-07.txt`, as fetched): status "Expired & archived", not an RFC, no intended status; latest revision 07 dated 2025-10-15 (page "Last updated 2026-04-18"). Text: makes POST/PATCH "fault-tolerant"; key SHOULD be a UUID or random; the same key MUST NOT be reused with a different payload and the server SHOULD reply 422; an in-flight duplicate SHOULD get 409; after completion return the original result; expiry optional but publish the policy; Security (section 5): low-entropy keys let attackers fetch other clients' cached responses; suggests a composite lookup key with attributes only the resource knows. Agents/AI: not mentioned.
- Stripe, https://docs.stripe.com/api/idempotent_requests (VERIFIED, as fetched; vendor doc, SECONDARY for our purpose): API v1 saves status code and body of the first request after execution begins and replays it "including 500 errors"; keys up to 255 chars, V4 UUID suggested; keys may be pruned after at least 24 hours; same key with different parameters errors; validation failures and concurrent-request conflicts are not saved and can be retried; GET and DELETE take no keys. API v2 behaves differently (retries complete failed work). Agents: not mentioned. Where MCP's `tools/call` retry sits relative to any of this: NOT FOUND (searched: spec tools page, MRTR page, Ruby SDK tools page; none mentions an idempotency key for tool calls).

Preview / dry-run then apply
- Terraform, https://developer.hashicorp.com/terraform/cli/commands/plan (VERIFIED, as fetched): plan "lets you preview the changes"; `-out=FILE` saves a plan to pass to apply; the page does NOT say a saved plan guarantees the same actions or is staleness-checked; a speculative plan "is not meant to be applied" and other changes may alter the result; saved-plan workflow "primarily intended for ... automation". Agents: not mentioned.
- Kubernetes, https://kubernetes.io/docs/reference/using-api/api-concepts/ (VERIFIED, read in two chunks; release not stated on the page text): with `?dryRun=All` admission, validation, defaulting and merge run, "changes are not persisted", and the final object is returned; "Kubernetes guarantees that dry-run requests will not be persisted in storage or have any other side effects". Agents: not mentioned.
- Both describe a preview as a separate request with no binding to a later apply, except Terraform's saved plan file. A server-issued preview token for MCP: no primary source; the nearest are MRTR `requestState` and State Handle Hijacking above.

Soft delete and undo
- Authoritative source: NOT FOUND (searched: Stripe/Google/AWS docs via web search; the first page of results was blogs only). SECONDARY, search snippets only, pages not opened: LogRocket "ux reversible actions framework" (recovery windows "typically 30 days"), tianpan.co "agent undo saga multi tool rollback" (agent undo as a compensating-action problem, some tool operations not reversible by API), developers.etg24.de soft-delete page. Do not cite as doctrine.

Optimistic locking
- RFC 9110 section 13.1.1 (VERIFIED, https://www.rfc-editor.org/rfc/rfc9110.html, June 2022, STD 97, as fetched): If-Match "is most often used with state-changing methods (e.g., POST, PUT, DELETE) to prevent accidental overwrites when multiple user agents might be acting in parallel"; origin server "MUST NOT perform the requested method if the condition evaluates to false"; MAY answer 412. RFC 6585 section 3 (VERIFIED, as fetched): 428 Precondition Required exists to prevent the lost update; example text says try `If-Match`. Kubernetes (above): a stale `resourceVersion` on PUT gets `409 Conflict`. Agents: none of these mention them. How a stale read in an agent's context maps to this: [Inferred], not sourced.

## 3. Agent-specific risk

- OWASP Top 10 for LLM Applications, LLM06:2025 Excessive Agency (VERIFIED, https://genai.owasp.org/llmrisk/llm062025-excessive-agency/, as fetched; the 2025 edition). Root causes: excessive functionality, excessive permissions, excessive autonomy. Mitigations listed: minimize extensions; minimize extension functionality ("read-only access when writing isn't needed"); avoid open-ended extensions (shell, URL fetch); minimize extension permissions; "execute extensions in the user's context" (OAuth with limited scope); "require user approval" for high-impact actions; complete mediation (enforce authorization downstream, not by the LLM's judgment); sanitize inputs and outputs. Damage-limiting, "don't prevent the issue": log and monitor, rate limit.
- OWASP agentic guidance exists. Index, https://genai.owasp.org/initiatives/agentic-security-initiative/ (VERIFIED, as fetched): "OWASP Top 10 for Agentic Applications for 2026" (published 2025-12-09 per its page; version not stated), "A Practical Guide for Secure MCP Server Development" (page date 2026-02-16, version not stated), "Agent Control Standard", others. The two pages I opened (Top 10 for Agentic, MCP Secure Dev Guide) are landing pages: their entry lists and text are behind a Download link I did not open. So what they recommend for write actions: NOT READ. Do not cite.
- Anthropic, "Mitigate jailbreaks and prompt injections", https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks (VERIFIED, no date on page): for indirect injection: put untrusted content only in tool results; say in the tool description what the content is and where it came from; JSON-encode third-party strings; "Limit Claude's access to sensitive data and actions" with least privilege; screen tool outputs with a small model; red-team the agent "and confirm that ... your screening and confirmation steps catch the rest". It does not define a confirmation protocol for writes.
- Anthropic, "How we contain Claude across products", https://www.anthropic.com/engineering/how-we-contain-claude (VERIFIED, as fetched; published May 25, 2026): "users approved roughly 93% of permission prompts"; approval fatigue; Claude Code default is reads allowed, writes/bash/network need approval; "Tool output is an attack surface even when the tool is trusted"; a read-only database agent "can be deployed more broadly than one that writes to production"; asks whether an agent should have its own principal identity or act as an extension of the user, "a blend of both"; Cowork uses a per-session scoped-down token revocable independently of the user's.
- Anthropic, "How we built Claude Code auto mode", https://www.anthropic.com/engineering/claude-code-auto-mode (VERIFIED, as fetched; published March 25, 2026): default block rules for destructive or irreversible actions; "It is not a drop-in replacement for careful human review on high-stakes infrastructure"; reports a 17% false-negative rate on real overeager actions; gives no explicit guidance for tool authors.
- Anthropic's engineering post on tool design (earlier report, 2025-09-11) was not re-read for writes; it was about tool shape.
- Simon Willison, "The lethal trifecta", https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/ (SECONDARY, practitioner, 2025-06-16, as fetched): private data + untrusted content + external communication; "avoid that lethal trifecta combination entirely". Mentions no human confirmation step.
- Net of what is VERIFIED: the authoritative lists (spec, OWASP LLM06, Anthropic docs) say: least privilege, act in the user's context, human approval for high-impact actions, enforce authorization server-side, log, rate limit. Anthropic's own measurement says approval prompts alone are weak. None gives a server-side write protocol.

## 4. Delegation and audit

- MCP authorization page (VERIFIED, above): the client makes requests "on behalf of resource owners"; token audience MUST be the MCP server (RFC 8707); "MUST NOT accept or transit any other tokens"; token on every request. It does not mention RFC 8693, an `act` claim, or marking an agent's request as distinct from the user's. NOT FOUND there (searched: the whole authorization page as fetched for "act", "token exchange", "delegation"; none).
- RFC 8693 (VERIFIED, https://datatracker.ietf.org/doc/html/rfc8693, January 2020, Proposed Standard, as fetched): impersonation = A gets all B's rights; delegation = "principal A still has its own identity separate from B"; `act` claim "provides a means within a JWT to express that delegation has occurred", nested `act` forms a history, only the outermost is the current actor for access control; `may_act`; `actor_token` params. It is a token-exchange protocol; MCP does not adopt it in the pages read. MCP's Enterprise-Managed Authorization extension (VERIFIED, https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization) uses an ID-JAG exchange at the enterprise IdP; the page does not mention `act`.
- Anthropic (above) frames agent identity as an open question: own principal, extension of the user, or a blend.
- OWASP Logging Cheat Sheet (VERIFIED, https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html, no date on page, as fetched): log "when, where, who and what": when (timestamps, interaction identifier); where (app, service, entry point); who (source address, user identity, a user-type classification e.g. public / authenticated / uptime monitor); what (event type, severity, security flag, description). Always log authorization failures, input validation failures, higher-risk functions including admin actions, data import/export. Never log tokens or session ids; hash/mask sensitive data; tamper detection; restrict and monitor log access. It says nothing about agents. How to tell an agent write from a human write: NOT FOUND (searched: OWASP Logging Cheat Sheet, MCP authorization and tools pages, RFC 8693 page). The user-type classification attribute is the closest source; recording the OAuth client (application) on every row is our design (the downstream app we know of does this).
- Spec side: clients SHOULD log tool usage; security best practices say token passthrough destroys the audit trail ("The MCP Server will be unable to identify or distinguish between MCP Clients"). Server-side audit of writes is not mandated.

## 5. Agent-facing CLI writes

- clig.dev (VERIFIED, https://clig.dev/, "no date" on page, as fetched): "Confirm before doing anything dangerous": interactive prompt for `y`/`yes`, otherwise require `-f`/`--force`; mild / moderate / severe tiers; moderate: "Consider giving the user a way to 'dry run'"; severe: make it hard to confirm by accident, e.g. type the resource name, plus scriptable `--confirm="name-of-thing"`. `-n/--dry-run`: "describe the changes that would occur". `--no-input`: "don't prompt or do anything interactive ... fail and tell the user how to pass the information as a flag"; prompt only if stdin is a TTY. Exit 0 on success, non-zero mapped to failure modes. "operations should be idempotent where possible". The page does not mention `--yes` and does not mention agents.
- gh, https://cli.github.com/manual/gh_repo_delete (VERIFIED, as fetched, version not stated): `--yes` "Confirm deletion without prompting"; when no repository argument is given "the `--yes` flag is ignored and you will be prompted"; deletion needs the `delete_repo` scope, obtained with `gh auth refresh -s delete_repo` (a scope step-up for a destructive command). Behaviour without a TTY: not documented on the page. gh env vars (`GH_PROMPT_DISABLED`, `GH_TOKEN`) are from the earlier report.
- RFC 8628 device grant (VERIFIED, https://datatracker.ietf.org/doc/html/rfc8628, August 2019, Proposed Standard, as fetched): for devices that "lack a browser" or have limited input; user code + verification URI on a second device; polling default 5 s, `slow_down` adds 5 s; section 5.4 remote phishing: tell the user they are authorizing a device. It does not mention CLIs.
- RFC 8252 (VERIFIED, https://datatracker.ietf.org/doc/html/rfc8252, BCP 212, October 2017, as fetched): native apps are public clients; MUST use an external user-agent; loopback redirect: "The authorization server MUST allow any port to be specified"; public native clients MUST use PKCE (RFC 7636); MUST NOT use embedded user-agents. This is the source for the loopback + PKCE shape Retask uses; RFC 8628 is the alternative for no-browser hosts.
- CLI vs MCP for writes, authoritative statement: NOT FOUND (searched: web search "CLI vs MCP for AI agents write operations authorization official guidance"; clig.dev; MCP spec tools/authorization pages; OWASP LLM06). Results were vendor/practitioner posts only (tyk.io, nhimg.org, nordicapis.com; snippets, not opened; SECONDARY): they argue a CLI enters the app's own execution path, MCP keeps session state, and write functions should be separated from read endpoints. One author's view, not a standard.

- What a test must prove for a write tool is not given by any source I read as a checklist. The proof items below come from the sources' MUSTs/SHOULDs and Retask's existing specs; mapping is [Inferred]:
  - authorization matrix (access controls MUST; State Handle: user bound to handle; OWASP complete mediation);
  - idempotent replay (draft IETF 422/409/replay; Stripe) - only if a key is adopted;

  - annotations match behaviour (the spec says hints are untrusted,) so a test of the code path is the only proof.

## Options for what to ship (no ranking, no recommendation)

A. Rewrite mcp-server.md for read + write (new section "Write tools").
 - Backing: spec tools/authorization/elicitation/MRTR pages, security best practices (State Handle Hijacking, Scope Minimization), OWASP LLM06:2025, Anthropic prompt-injection and containment posts (all VERIFIED above).
 - Kind: MIXED. Each cited MUST/SHOULD is an external claim (doctrine-verifier gated, each quote re-verified against a version). The policy (which writes, confirm or not, scope names) is our design (maintainer decision). Must be split per CLAUDE.md "split a mixed change". Owner ruling on #2034/#2049 currently keeps shipped doctrine read-only.
 - Main risk: nothing in the sources gives a server-side write protocol; the file would present our design beside spec text, and no downstream app has run a write tool, so every write rule is untested in practice.

B. A per-project decision checklist (not rules): five or six decisions each project records in its CLAUDE.md before adding a write tool (scope per write; confirmation channel and what happens for a client without elicitation; idempotency; audit row for writes naming the OAuth client; rate limit key; irreversible actions refused).
 - Backing: the same sources; the reviewer on #2034 suggested this shape. Citations for mechanisms, none for policy.
 - Kind: OUR DESIGN for the checklist's existence and wording; EXTERNAL for each cited mechanism.
 - Main risk: a checklist can pass review with every answer "no" and gives no mechanism; a project can copy a wrong answer.

C. Extend the `mcp-annotations` gate to write tools (plugins/rails-flow/scripts/check_mcp_annotations.py, which today requires `read_only_hint` and `open_world_hint`).
 - Backing: schema.ts defaults (VERIFIED) show an unset `destructive_hint` reads as destructive and an unset `idempotent_hint` reads as non-idempotent only when `read_only_hint` is false; the spec says annotations are untrusted hints, so the gate proves only that the source states them.
 - Kind: OUR DESIGN (a gate rule); the annotation semantics are external (verified).
 - Main risk: a gate that reads hints can be green on a tool that writes while declaring read-only (the hints are untrusted by the spec's own wording); needs a negative test (a tool with `read_only_hint: true` whose code path writes) or it is a gate that cannot fail.

D. Agent-facing CLI doctrine (when allowed, how to authenticate, how to confirm).
 - Backing: RFC 8252 (loopback + PKCE + external user-agent), RFC 8628 (alternative with no browser), clig.dev (confirm tiers, `--dry-run`, `--force`, `--no-input`, `--confirm=name`), gh docs (scope step-up for destructive commands; `--yes` rules) (all VERIFIED); Retask's CLI as one working read-only example.

 - Main risk: clig.dev is advice with no date and not about agents; the Retask CLI never wrote data, so write behaviour (dry-run, confirm tokens in a non-interactive agent session) is unproven.
