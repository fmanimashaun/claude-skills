# Internationalisation

**Situational, and declared once.** Most apps are monolingual, and demanding locale files everywhere
is the false positive that gets a rule ignored. So `/rails-flow:setup-flow` asks, and the answer is
**recorded** — `config.x.locales` — which is what lets a check have three honest states instead of
two: conforming, drifted, and *not applicable because this project declared monolingual*. Same
mechanism as `config.x.brand.pack` (#788): a check that cannot tell what a project chose has not
measured anything, and guessing produces confident, wrong remediation.

```ruby
# config/initializers/locales.rb
Rails.application.configure do
  config.x.locales = %w[en]                 # monolingual — one element, still declared
  # config.x.locales = %w[en ar fr]         # multi-locale
end
```

Declaring `%w[en]` is not ceremony. It is the difference between *"this project chose one locale"*
and *"nobody has thought about it"*, and only the first can be checked.

## 1. Setup

```ruby
# config/application.rb
config.i18n.available_locales = %i[en ar fr]
config.i18n.default_locale = :en
config.i18n.fallbacks = true          # a missing key falls back rather than rendering the key name
```

`available_locales` is an allow-list: an unknown locale raises rather than silently rendering
English, which is what you want when the locale arrives from a URL.

**Add `rails-i18n`.** Rails ships English translations for its *own* strings — validation messages,
date and number formats, month names — and nothing else. Without the gem those stay English while
your copy translates, which reads worse than an untranslated app because it looks broken rather than
unlocalised.

```ruby
gem "rails-i18n", "~> 8.1"    # the release line tracks Rails; ~> 8.1 for Rails 8.1
```

## 2. Choosing the locale — `around_action`, never `before_action`

```ruby
class ApplicationController < ActionController::Base
  around_action :switch_locale

  private

  def switch_locale(&action)
    locale = params[:locale] || I18n.default_locale
    I18n.with_locale(locale, &action)
  end
end
```

**`I18n.locale = …` in a `before_action` leaks.** The Rails guide states it plainly: *"I18n.locale
can leak into subsequent requests served by the same thread/process if it is not consistently set in
every controller… For that reason, instead of `I18n.locale =` you can use `I18n.with_locale` which
does not have this leak issue."*

That is not a style preference. Puma is the default server and it is **threaded**: threads are
reused across requests, so a locale set and never reset is inherited by whoever gets that thread
next. The bug is invisible under single-threaded local testing and surfaces in production as a page
served in the previous visitor's language.

`I18n.with_locale` restores the previous value when the block exits, which is why it must wrap the
action — an `around_action`, not a `before_action`.

## 3. Locale files and lazy lookup

```yaml
# config/locales/en.yml
en:
  invoices:
    show:
      title: "Invoice %{number}"
```

```erb
<h1><%= t(".title", number: @invoice.number) %></h1>
```

The leading dot scopes the key to the view's own path, so `app/views/invoices/show.html.erb` reads
`invoices.show.title`. Move the file and the key moves with it.

**Lazy lookup is a VIEW-HELPER feature only.** The Rails guide is explicit: *"Automatic translation
scoping by partial is only available from the `translate` view helper method."* In a controller,
mailer, model or job, `t(".title")` resolves to nothing sensible — write the full key.

Interpolate with `%{}`; never build a sentence by concatenating translated fragments, because word
order differs between languages and a translator cannot reorder fragments they never see together.

## 4. `lang` and `dir` on `<html>`

```erb
<html lang="<%= I18n.locale %>" dir="<%= t("i18n.direction", default: "ltr") %>">
```

```yaml
# config/locales/ar.yml
ar:
  i18n:
    direction: rtl
```

Direction belongs to the locale, so it lives in the locale file rather than a Ruby case statement
that must be edited every time a language is added.

**The CSS half is already done, and it is the half that matters.** `design-system`'s
`foundations-tokens.md` prescribes logical properties — `padding-inline`, `margin-block`, `inset` —
precisely so direction is not baked into the stylesheet. **If every component uses them, flipping
`dir` already works.** RTL is normally painful because physical properties (`padding-left`,
`margin-right`) are written everywhere and then retrofitted; the retrofit is the project, not the
switch. This file only has to set the attribute.

Screen readers also use `lang` to select a voice, so it is an accessibility attribute before it is an
i18n one — set it even in a monolingual app.

## 5. What NOT to translate

- **Enum values, state names, and anything a query filters on.** Translate the *label* at render
  time; the stored value stays canonical. A translated enum makes `where(status: "paid")` match in
  one locale and not another.
- **Database-backed content.** Locale files are for interface copy. User-entered content needs a
  translation table or per-locale columns, which is a schema decision rather than an i18n one.
- **Log lines, error classes, job names, audit trails.** Operators read these and tooling matches
  them; a localised log is a log you cannot grep.
- **Money and dates — localise the FORMAT, not the value.** `number_to_currency` and `l(date)` take
  the locale's format; the underlying value is one number and one instant. See
  `performance-caching.md` on storing money as integer cents.

## 6. Testing

```ruby
it "renders the invoice heading in French" do
  I18n.with_locale(:fr) { get invoice_path(invoice) }
  expect(response.body).to include(I18n.t("invoices.show.title", locale: :fr, number: invoice.number))
end
```

**Assert against the key, not the English string.** A spec pinning `"Invoice 42"` fails the moment
copy is edited and passes when the translation is missing — exactly backwards. `testing.md` §9 makes
the same point about error keys surviving i18n.

**One spec worth having per locale**: every key a view references exists in every declared locale. A
missing key renders the key name — `invoices.show.title` on the page — which is obvious in review and
invisible to a test that never rendered that locale.

## Not in scope here

**Machine translation, translation-management services, and per-locale routing beyond
`params[:locale]`.** Each is a product decision with its own operational cost, and none is needed to
serve a second language correctly. Reach for them when a translator, not a developer, is maintaining
the copy.
