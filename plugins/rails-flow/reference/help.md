# Help & SOP — generated from the repository

The interface carries the name, the unit, the state and the action. The explanation lives in Help. And Help is
not typed into the app: it is **authored beside the spec, reviewed through a PR, joined with the app's own
registries, and built into one file the app renders read-only**, stamped with the release it describes.
(Owner's ruling, Retask, 5 Sep 2026: "we will prefer to generate all documentation and procedure, well
researched, via the repo.")

## The layout

```
docs/product/help/
  registry.json          the app's OWN dump of its settings, permissions and screens (see below) — never typed
  procedures/*.md        one procedure each   — frontmatter: title:, area:, spec: (the § it derives from)
  rules/*.md             one enforced rule    — frontmatter: title:, spec:
  glossary/*.md          one term each        — frontmatter: term:, versus: (the word it is not)
  screens/<key>.md       one guide per screen — frontmatter: screen: <key from the registry>; title from the registry
  _build/help.json       GENERATED by build_help.py; the app reads this and nothing else
```

`spec:` is required on procedures and rules: a procedure with no section behind it is opinion, not doctrine.
Every screen in the registry needs a guide, every guide needs a screen — the Help link on a screen opens its guide.

Help is **scoped to the signed-in role**: `roles: Admin, Freelancer` on any page names whose Help it belongs to,
and no `roles:` line means every role. The build splits it into a `roles` list and carries the rest of the
frontmatter as `meta` — a procedure's `summary:`, the `rules:` it rests on and the `screens:` it applies to, a
guide's `permission:` and `purpose:` — so the app renders the index, the related links and the guide's meta box
from the one file and never re-reads the sources.

## The registry is the app's, not a document

`docs/product/help/registry.json` is produced by the application from its own code, so a setting, permission or screen
cannot exist without appearing here — and `help-drift` refuses a build where one appears here without its Help.
A rake task in the project writes it; this is the shape:

```json
{
  "commit": "abc1234", "version": "v0.4.0",
  "settings":    [{ "key": "task_aging_hours_before_escalation", "label": "Aging hours before escalation", "unit": "hours",
                    "group": "queue", "what": "Unclaimed this long and the task is flagged as aging.",
                    "affects": "The dashboard's aging figure and the Throughput report." }],
  "permissions": [{ "key": "screen_defect", "name": "Screen and attribute a defect",
                    "allows": "Decide fault on a filed defect.", "roles": ["Admin"] }],
  "screens":     [{ "key": "defects", "area": "Accountability", "label": "Defect queue",
                    "purpose": "Filed defects awaiting screening.", "permission": "screen_defect" }]
}
```

The task reads the registries the app already has — its settings table or registry object, `Role::PERMISSIONS`
with a descriptions table, its navigation catalogue — and writes the file. Skeleton:

```ruby
# lib/tasks/help.rake
namespace :help do
  desc "Dump the settings, permissions and screens registries for build_help.py (docs/product/help/registry.json)"
  task registry: :environment do
    registry = {
      commit: `git rev-parse --short HEAD`.strip,
      version: ENV.fetch("APP_VERSION", "dev"),
      settings: Setting.registry.map { |s| { key: s.key, label: s.label, unit: s.unit, group: s.group, what: s.what, affects: s.affects } },
      permissions: Role::PERMISSIONS.map { |key| { key: key, name: Role::PERMISSION_NAMES.fetch(key), allows: Role::PERMISSION_ALLOWS.fetch(key), roles: Role.holding(key).map(&:name) } },
      screens: Navigation.screens.map { |s| { key: s.key, area: s.area, label: s.label, purpose: s.purpose, permission: s.permission } }
    }
    path = Rails.root.join("docs/product/help/registry.json")
    path.dirname.mkpath
    path.write(JSON.pretty_generate(registry) + "\n")
    puts "wrote #{path.relative_path_from(Rails.root)}"
  end
end
```

`Role::PERMISSION_NAMES` and `Role::PERMISSION_ALLOWS` are the description tables the app must carry: a
permission the registry cannot describe is a permission the interface would have to explain, which is the
thing being removed.

## Build and check

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/build_help.py"            # write docs/product/help/_build/help.json
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/build_help.py" --check    # DRIFT if the committed build is not clean
```

Exit 0 written / clean · 1 DRIFT · 2 PROBLEM · 3 not applicable (no registry; or `--check` before the first
build). PROBLEMs: a screen with no guide, a guide for an unknown screen, a procedure or rule with no `spec:`, a
setting with no `what`, a permission with no `allows`, a build that dropped a page. The `help-drift` check runs
`--check` in `/rails-flow:toolchain-audit` and CI once the registry exists.

## What the app does with the build

`help.json` holds every page's rendered HTML (tags: `p strong em code h2 h3 ol ul li blockquote a` — the writing
subset, nothing that runs), the three references, a search index, the commit and version. The app renders it
read-only in every shell's Help & SOP, links each screen to its guide by key, and shows the version on every page.
Nothing in Help is edited in the interface; a change is a commit with a reason, reviewed, and lands with the deploy.

## What this is not

Not the developer wiki. `docs/wiki/` mirrors the codebase for developers and agents; Help is the user's manual.
They share one discipline — rendered from structured sources, drift-checked against HEAD — and nothing else.
