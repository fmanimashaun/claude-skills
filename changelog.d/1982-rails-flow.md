section: rails-flow
- **`git add` of a path inside the repository, and a `git` run with a hermetic `GIT_CONFIG_*` environment, are no longer refused; the taint of a `git add` is read from its own words — `plugins/rails-flow/git-shim/git`, `plugins/rails-flow/hooks/scripts/guard-bash.sh`, `plugins/rails-flow/hooks/scripts/lib/normalize_cmd.sh`, `plugins/rails-flow/hooks/scripts/session-start.sh`** (#1982, a regression in v1.156.0). Three refusals hit ordinary work. (1) `guard-bash.sh` refused any command holding a `git add` and a `~`, a `$`, a backtick, `{` or `}` ANYWHERE in it, so `cd ~/projects/x-wt/rbk && git add -- docs/a.md && git status` (a tilde in the `cd`) and `git add f && git commit -m "$(cat <<'EOF' ... EOF)"` (the shape CLAUDE.md tells agents to commit with) were refused with "stage specific files by plain relative path", reported from a session working in a linked worktree. The taint is now read from the words of the `git add` command itself: the normaliser leaves an unquoted `$V`, a backtick, `{`, `}` and `~` in the segment of the command they sit in, and a second opt-in pass (`NC_MARK_EXPANSION=1` in `_dequote`, off by default so no other rule reads different text) leaves a `$` where a double-quoted span holding an expansion was deleted (`git add f "$V"`, `"$(echo -A)"`); `V=-A; git add $V`, `git add $(echo -A)`, `git add ~/x`, `git add {a,b}`, `git add f "$V"` and `bash -c "git add $V"` stay refused. (2) Both the shim and `guard-bash.sh` refused an ABSOLUTE `git add` path, which is how a session in a worktree often names a file; one that resolves, physically (`cd … && pwd -P`, because git reports the toplevel physically and a temp directory is often a symlink), to a path STRICTLY INSIDE the toplevel of the repository git runs in now passes. The root in any spelling (`/abs/repo`, `/abs/repo/`, `/abs/repo/.`), a sibling directory that merely starts with the repository's name, a path outside it, a `..` and a glob stay refused. (3) The shim refused EVERY git command, `git init` included, whenever ANY `GIT_CONFIG_*` variable was set, and the hermetic fixtures (`fixture_git.hermetic()` and its copies, in this toolchain and downstream) export `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`, so a selftest that runs git failed on its first call under the shim (six Retask toolchain selftests). The shim now READS the pairs and takes an ALLOWLIST of (key, value) pairs (the coordinator's decision on #1982), the same one for `GIT_CONFIG_KEY_n`/`VALUE_n`, `-c`, `--config-env=` and `--config-env`: the keys a hermetic fixture sets with any value (`scripts/fixture_git.py`: `maintenance.auto`, `gc.auto`, `user.name`, `user.email`, `commit.gpgsign`), plus the exact hardening overrides shipped code passes, with exactly that value (`core.fsmonitor=false`, `core.hooksPath=/dev/null`, `core.quotePath=false`, `tag.gpgSign=false`, an EMPTY `credential.helper`) and `credential.helper=!gh auth git-credential`, that exact string only (shipped `remote_evidence.py` needs it and it runs our own gh). Keys match exactly and case-insensitively (`user.name.x` is not `user.name`), values exactly (`core.fsmonitor=true`, `core.hooksPath=/tmp/x`, `credential.helper=!gh auth git-credential --evil` are refused); a `-c name` with no `=` is the value `true`, and `--config-env name=VAR` is judged with the value VAR holds (an unset VAR is refused). Every other key is refused: `core.pager`, `core.editor`, `credential.helper` with another value, `gpg.program`, `core.sshCommand`, `include.*` and an alias given with `-c`. `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_SYSTEM` naming anything but `/dev/null`, a count that is not a plain number and any other `GIT_CONFIG_*` name stay refused; `GIT_CONFIG_GLOBAL` is `/dev/null` or a regular file (not a symlink) physically strictly inside the temp root whose every entry, read with the real git, passes the same pair rule (an include, a line that is not `key=value`, anything not allowlisted refuses it). (4) Decision (b): a hermetic fixture may stage its OWN temp repository whole. The shim refused `git add -A` everywhere, so every selftest that does it failed when run from the Bash tool; `add` is now exempt only when GIT_DIR and GIT_WORK_TREE are both set and, physically resolved, both lie strictly inside TMPDIR (which must be set, and must not be `/`, HOME or an ancestor of HOME), and the work tree is neither the session's project toplevel nor an ancestor of it. The project is recorded by the SessionStart hook in `CLAUDE_SESSION_PROJECT_TOP` (the physical toplevel, once, nothing outside a repository); where it is unset the exemption does not apply. Only `add` is exempt (`reset --hard` and `clean -fd` stay refused in the fixture). The temp root is TMPDIR and must be set, must not be `/` or HOME, and must not contain the project. Cause measured on exports of the tags: v1.155.0 allowed all of these (it had no shim and no add allowlist), v1.156.0 refuses; `git commit -- <path>` was checked and is NOT a bypass (it cannot commit an untracked file). 53 guard-bash probes and a second adversarial pass of over 40 probes found no hole: a symlink inside the repository to `/` or to a directory outside it, `..` after a symlink (git collapses it lexically too), `export`/`set --`/`read`, `xargs`, `command`, `env`, `time`, loops, line continuations, ANSI-C words, a heredoc after the add. Left allowed on purpose: a `$(...)` or `~` in an environment prefix (`FOO=$(date) git add f`), which does not reach the pathspec; and an absolute path from a `cd`'d directory is judged against the hook's own working directory, not the one the command `cd`s to (use the relative path there). Our own design; the decision this narrows is the coordinator's on #1783, recorded on #1982. Follow-up (#1994): the fixture exemption no longer trusts `CLAUDE_SESSION_PROJECT_TOP` alone. An inline `CLAUDE_SESSION_PROJECT_TOP=/usr TMPDIR=<parent> GIT_DIR=<project>/.git GIT_WORK_TREE=<project> git reset --hard` was allowed on the real project (reproduced by probe); `plugins/rails-flow/hooks/scripts/session-start.sh` now also writes a `claude-session-project` file into the session repository's common git dir and `plugins/rails-flow/git-shim/git` refuses the exemption for any repository carrying it (a linked worktree's `commondir` included), whatever the environment says. Left as is: a fixture exemption for a different real repository under a temp root that does not contain the session project.
