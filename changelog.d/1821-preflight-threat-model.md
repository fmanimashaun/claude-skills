Its acceptance asked first whether a project's settings or a repository can reach a plugin PreToolUse hook's environment; the docs say yes: a committed `.claude/settings.json` `env` block "reach[es] every subprocess Claude Code starts", hooks inherit it, it applies once the workspace is trusted and in `-p`/SDK runs unless the user opts out, whether `PATH`/`PYTHONPATH`/`LD_PRELOAD`/`DYLD_*` are filtered is INCONCLUSIVE (absent from the ignored list, which says "They include"), and "PreToolUse hooks run before the permission prompt" (settings-reference#env, hooks, permissions, read 2026-10-12). Neither is built: (a) a project preflight script, because a project's own settings file can already declare that PreToolUse hook under the same trust, so the plugin must not be a second execution vector for repository code; (b) an automatic Postgres restart, because it is a side effect before approval. The record also states what the shipped `test-preflight.sh` already does (`/bin/bash -p`, #1850's environment scrub, an isolated `python3` from a trusted directory) and the three residual, harness-level gaps, and classifies the hook as advice under harness-doctrine §10. No code changes. Our own design, decided by the acceptance the maintainer recorded on #1821.
