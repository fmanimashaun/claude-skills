section: rails-flow
- **Every rails-flow hook starts `/bin/bash -p` and sources `hooks/scripts/lib/trusted-env.sh` first — `plugins/rails-flow/hooks/hooks.json`, `plugins/rails-flow/hooks/scripts/lib/trusted-env.sh`** (#1850; P1 of #1843; our own design, the owner's decision recorded on #1850). A repository's checked-in `.claude/settings.json` `env` reached every hook process: 10 hook commands started under a repository-chosen `bash`, `python3` resolved to the repository's, `PYTHONPATH`, `GIT_CONFIG_*` and `BASH_ENV` were honoured (measured on #1843). All 15 rails-flow hook commands now start `/bin/bash -p`, and the lib, sourced as each script's first executable line, unsets `PYTHON*`, `LD_*`, `DYLD_*`, `NODE_OPTIONS`, `BASH_ENV`, `ENV`, `SHELLOPTS`, `BASHOPTS`, `CDPATH`, `GLOBIGNORE` and every `GIT_*` outside an allowlist, and rebuilds `PATH` from absolute entries outside the repository (the outermost Gemfile or .git ancestor of the working directory, symlinks resolved). It uses shell builtins only, bounded loops and bash 3.2, the requirements of the #1826 review. `rf_trusted_python` is available for a script that wants an interpreter whose link target is outside the repository too. What it does not close: `disableAllHooks` and a repository's own settings hooks, so the guarantee is still inside a trusted workspace. A system with no `/bin/bash` (NixOS) cannot start a hook, which is a non-blocking error: a gate fails open there. Tested by `python3 plugins/rails-flow/scripts/check_hook_gates.py --only hostile_env`, red on `dev` for every hook before this change.
