section: rails-flow
- **`git config` writes through the git shim are an allowlist — `plugins/rails-flow/git-shim/git`, `plugins/rails-flow/scripts/git_shim_selftest.py`, `plugins/rails-flow/scripts/mutations/git_shim.py`** (#2043, the coordinator's decision, a follow-up to #2021). Blocking program-running keys one at a time never closed the class: a0 measured a dozen more after #2021's eight (`pager.*`, `core.askpass`, `core.gitProxy`, `diff.*.textconv`/`command`, `filter.*.clean`/`smudge`/`process`, `merge.*.driver`, `*tool.*.cmd`, `web.browser`, `uploadpack.packObjectsHook`). A write is now let through only for `CONFIG_WRITE_ALLOWED`: identity, signing, branch tracking, `remote.*.url`/`fetch`, a few pull/push/fetch preferences, plus `alias.*` and the credential-helper keys, whose dangerous values have their own rules. That set was measured from our scripts and the downstream fixtures. Every write spelling is judged: the `set`/`unset`/`edit` subcommands, the write flags in git's unique-prefix spellings, and the old `key value` form, with option values never read as the key. `--edit` is refused, and so is a combined short-option cluster (`-ze`, `-zf FILE`, `-fFILE`: git reads it letter by letter, so it can edit or move the key; found by the commit security review), and so is any long option that is not an exact, known flag: an abbreviated VALUE option (`--fil x` = `--file x`) moves the key the same way (found by a second review). #2021's per-key program-key rule is removed as superseded, so a READ of such a key (`git config --get core.editor`) now runs. `core.fsmonitor`/`core.sshCommand` stay refused even to read (the #1789 hooks rule), and the section-rename refusal stays: `alias.*` is allowlisted, so renaming `alias.x` onto `core` is stopped only by it. A selftest case with a row per refused class, the allowlist and the read forms; sixteen mutants, one per mechanism and one per refused class. Our own design; no framework claim.
